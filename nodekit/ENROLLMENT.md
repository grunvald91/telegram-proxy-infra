# MNEBYVPN Nodekit — отдельная криптографическая идентичность нового узла

Статус: OFFLINE SECURITY LIBRARY. В production пока нет сервиса автоматической регистрации, локального Xray-prover, controller issuer, выдачи новых узлов или доступа с реальных клиентских сетей.

## Доверенная цепочка

1. После нового Nodekit `stage` на только что полученном VPS создаётся собственная пара Ed25519. `create-node-identity.mjs` записывает закрытый ключ только в root-owned закрытую директорию узла, печатает лишь публичный SPKI и его SHA-256. Не переносить WG/REALITY/TLS ключи старого узла, не экспортировать private key в GitHub Actions, LLM, web-подписку или бот.
2. Центральный controller с полномочиями registrar проверяет уникальность node_id, отсутствие совпадения host/port, public key, подтверждённую страну egress, remote service identity, E2E и hard expiry. Он регистрирует публичный ключ узла в защищённой базе.
3. При создании или продлении **конкретного** права доступа controller выдаёт узлу короткоживущий случайный nonce. Только локальный процесс узла, после реальной проверки, что Xray активировал этот entitlement и его серверное истечение срока, подписывает результат своим Ed25519 ключом (node observation).
4. Контроллер сверяет node observation с источником истины — активным entitlement, revision/expiry, nonce, текущей страной egress и E2E подтверждениями, затем создаёт вторую подпись Ed25519 над точной версионированной записью `MNEBYVPN_NODE_ACCESS_V1`.
5. Подписанная запись попадает в ограниченную таблицу `vpn_additional_node_receipts`, и сайт читает её только при включённых двух release-флагах. Сайт знает лишь публичный ключ контроллера и не выдаёт новую запись без валидной подписи. Действующие ссылки и старые профили не изменяются.

## Исходники и контракт

- `nodekit/create-node-identity.mjs`: создаёт уникальную локальную идентичность на подготовленном новом узле. Сейчас требуется предварительный Node.js 22 и staged node; **это не универсальный установщик**.
- `nodekit/grant-issuer.mjs`: функции `signNodeObservation` и `issueWebsiteGrant`, проверка ключа и доказательных полей, ABI `websiteReceiptMessage` совпадает с `packages/provisioning/src/multi-node-subscriptions.ts` репозитория Mnebyvpn (PR #157). Внимание: сама функция `signNodeObservation` не проверяет живой Xray — это должна делать отдельная доверенная локальная служба.
- Для тестов используется только встроенная криптография Node.js, без зависимости от сторонних библиотек.

## Неизменяемые ограничения

- Подписанный профайл не является доказательством качества сети: внешние E2E, контроль географии egress и ограничение прав проверяются отдельно.
- Controller nonce должен выдаваться атомарно, иметь TTL и гаситься после использования; ledger replay-защиты ещё нет. До его реализации не разрешать выдачу в production.
- Controller signing key, node private identity и токены инфраструктуры должны быть **разными** ключами. Центральный API агент никогда не получает ни один из них; он может лишь запросить допустимый runbook.
- При недоступности controller/node или устаревшем proof — не выдавать дополнительный узел в новых подписках; старый узел продолжает работать.
- При глобальной неисправности агент собирает только безопасные метрики и хэши и запрашивает разрешение владельца. Не получает root shell.

## Следующий выпуск

Отдельный API enrollment с одноразовым токеном и строгим node_id; протокол node-observation на реально работающем Xray, атомарный nonce ledger, защищённый controller signer, синхронизация действующих entitlements/отзыва по всем узлам, периодические независимые E2E и первый новый VPS canary. Только после этого включать чтение подписей в production.
