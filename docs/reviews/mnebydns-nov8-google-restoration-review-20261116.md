- Actual files reported changed: `/opt/mnebydns-dot/Corefile` (one Google-only A answer from RU188 to DE89), `/etc/mnebydns-googlepilot/nginx.conf` (proxy_timeout 15m to historical 120s).

## Findings

### P1 — One-off production workflow was left push-triggered — FIXED

Previous diagnostic-branch workflow allowed a push to its YAML to cause a fresh production restoration attempt with SSH credentials. The already-deployed, hash-pinned script is not idempotent. It rejected a repeat because expected old config hashes no longer match.

**Fix:** Replaced workflow with an inert, manual-only archival job in commit [cc964302](https://github.com/grunvald91/telegram-proxy-infra/commit/cc964302f015cf38bcaa2da1fa30d9ce27d7740d). No production server was modified by this archive.

### P1 — Scope is narrower than "restore all Google domains to 8 November" — OPEN

`restore_dns()` checks that historical A template headers exist, but does not compare all answers, CNAME/AAAA/HTTPS/SVCB behavior, precedence or exact route bodies against 8 November. It changes only one appended six-host rule. Existing post-November 8 Google SNI domains and expanded wildcard regexes were deliberately retained. Consequently the successful run is a **selective legacy Google correction**, not a byte-for-byte restoration of all 8 November Google routes and not proof of coverage for every Google-related domain.

### P1 — Blind rollback can overwrite an intervening production change — OPEN

`rollback.sh`, generated by `rollback_contents`, uses unconditional `cp -p <backup>.before <target>`. No comparison with the exact staged bytes is done before rollback. There is also no shared public-route `flock` lock around read/backup/write/reload. A concurrent production update during a failed deployment could be lost. The completed successful run reports `rollback_armed=false`, so this finding concerns unsafe reuse, not a proven incident.

### P2 — No reboot-persistent rollback while a deployment is underway — OPEN

`systemd-run --on-active=6m` arms a transient timer, unlike the original 8 November persistent calendar watchdog. If reboot occurs during an uncommitted deployment, guaranteed recovery is not demonstrated. Successful run explicitly stopped its timer.

### P2 — Atomic write does not preserve file uid/gid or all metadata — OPEN

`durable()` writes a new temporary file and uses `os.replace`, applying only mode bits. The original `uid`, `gid`, ACLs and security metadata are not copied. Whether live ownership actually changed is **not verified**. The service-active result does not establish metadata parity.

### P2 — Validation and JSON status claims too strong — OPEN

`OUT["non_google_routes_preserved"]` and `OUT["customer_access_untouched"]` are initially set to `True` rather than independently checked. The final `production_services_healthy` requires active service state plus file hashes, not end-to-end DoT or Google app functionality. Do not use this result as proof of customer-side playback.

### P2 — 120-second historical GooglePilot timeout is a behavior change — NOTE

The timeout was intentionally restored from `15m` to `120s`. This is an inactivity timeout, not a hard maximum video length; lower idle tolerance is still a functional difference, and this review has no application playback evidence.

## Verdict and next action

**Historical Google route restoration: partially completed, with verified successful application of two targeted changes. Full November 8 parity and Google application functionality: not confirmed.**

Do not rerun the old production script. Any subsequent change should use a new reviewed one-shot flow that:
1. derives a structured old/current Google-domain policy diff without overwriting non-Google or personalised configuration;
2. preserves uid/gid/mode, uses an exclusive lock and checks staged hashes again immediately before swapping;
3. uses rollback conditioned on ownership plus a reboot-persistent watchdog;
4. separates configuration integrity from end-user application verification.

This review did **not** change production.
