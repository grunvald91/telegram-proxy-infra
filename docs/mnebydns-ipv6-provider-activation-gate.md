# MNEBYDNS #84 — IPv6 /64 у FirstVDS: подтверждённые препятствия и порядок запуска
Дата проверки: 2026-11-12. **Только read-only.** Не выполнялись изменения на RU/foreign VPS.

## Фактическое состояние VPS

Подтверждено текущим [read-only CI](https://github.com/grunvald91/telegram-proxy-infra/actions/runs/43163952073):

| Проверка | RU (188) | FOREIGN (89) |
|---|---|---|
| IPv6 отключён в настройках ядра/интерфейсов | **Да** | Нет |
| Обнаружен глобальный IPv6 | 0 | 0 |
| Есть IPv6-маршрут в интернет | Нет | Нет |
| IPv6 TCP listener | Да | Да |
| Принадлежность аккаунта провайдеру | не проверялась | не проверялась |

На RU: `99-disable-ipv6.conf` задаёт `net.ipv6.conf.all.disable_ipv6=1` и `net.ipv6.conf.default.disable_ipv6=1`. IPv6 не отключён через параметр ядра `ipv6.disable=1`. Не изменять этот файл и не применять `sysctl --system` до выделения публичной подсети и плана отката. Отключение IPv6 могло быть намеренной защитой существующей сети — его причина пока неизвестна.

На FOREIGN ОС поддерживает IPv6, но ни публичный адрес, ни маршрут не назначены. Нет подтверждения, что зарубежный VPS оплачивается через FirstVDS: его имя не доказывает провайдера.

## Проверенный вариант RU у FirstVDS

В инвентаризации RU hostname заканчивается на `fvds.ru`. FirstVDS **публикует** услугу IPv6-подсети `/64` за **20 ₽/месяц** для VMmanager 6, но доступность по текущему серверу/тарифу до входа в биллинг **не подтверждена**.

- Официальная инструкция: [Заказ IPv6 на сервере с VMmanager 6](https://firstvds.ru/technology/zakaz-dopolnitelnogo-ip-adresa-dlya-virtualnogo-vydelennogo-servera).
- Официальная инструкция: [Добавление дополнительного IPv6](https://firstvds.ru/technology/kak-dobavit-ip-na-server).

Для VMmanager 6: `my.firstvds.ru → Товары → Виртуальные серверы → Изменить → IPv6-подсеть`, требуется **перезагрузка сервера** в процессе активации. Провайдер пишет, что в VMmanager один IPv6 добавляется автоматически, а дополнительные адреса из диапазона требуют ручной настройки. Из этого **не следует**, что произвольные миллионы адресов /64 автоматически доставляются до сервера для отдельного TLS listener; требуется отдельное подтверждение способа маршрутизации всего блока.

## Обязательный запрос в FirstVDS перед расходами/перезагрузкой

Для конкретного RU VDS необходимо получить письменный ответ:
1. Поддерживает ли тариф IPv6 /64 и есть ли услуга в текущем аккаунте (заявленная публичная цена 20 ₽/мес)?
2. **Маршрутизируется ли весь /64 на интерфейс VDS без отдельного добавления каждого IPv6 в VMmanager**, включая одновременный входящий TCP/443 на десятки/сотни адресов?
3. Требуется ли перезагрузка VDS для подключения /64 и возможно ли провести подключение с управляемым downtime без изменения IPv4?
4. Какой действительный IPv6 prefix, gateway, link-layer/NDP и требуемая модель настройки (per-IP /128, ND proxy, kernel local route)? **Не выбирать вариант наугад**.
5. Разрешены ли прозрачная TCP/SNI проксизация, большое число клиентских IPv6 и IPv4 egress к зарубежным HTTPS-ресурсам по правилам хостинга?

## Пошаговый GO/NO-GO (будущий, без текущего исполнения)

1. **CHECK ONLY:** зафиксировать текущие DNS/VPN/TG baseline, все критические TCP/UDP порты, доступ по IPv4, отдельный out-of-band VNC и свежий пригодный backup. Отсутствие backup/VNC = NO-GO.
2. **Договор с провайдером:** подтвердить не только /64 в панели, но и сетевую маршрутизацию всего диапазона на конкретный VDS. Если возможно только ручное подключение единичных IPv6, оценить масштабируемость, не считать пул готовым.
3. **Управляемая пауза:** согласовать окно обслуживания для RU, так как инструкция FirstVDS прямо требует reboot. Откат обязательно проверять через VNC/панель; автоматический rollback с отключением IPv6 не заменяет доступ к консоли.
4. **Только после выделения блока:** снять backup `99-disable-ipv6.conf`, проверить источник управления сетью (не предполагать netplan: на RU он не обнаружен), под разрешённую конфигурацию включить IPv6 с отдельной проверкой неизменного IPv4 маршрута. Никаких `sysctl --system` вслепую.
5. **Preflight post-activation:** на RU `public_ipv6_assigned_count>=1`, `ipv6_main_default_route=true`, `ipv6_route_to_public_resolver=true`; затем независимая проверка **входящего IPv6/TCP** с другого AS, а не только `curl -6` на самом сервере.
6. **Адресное доказательство:** сервер должен принимать TCP на *два различных* назначенных IPv6, определять различный `socket.localAddress` и возвращать **разные** оплаченные entitlement IDs. Изменение DNS/HTTPS маршрута в рабочем прокси только после такого отрицательного и положительного E2E.
7. **Клиенты:** Android Private DNS, iPhone encrypted DNS profile, Wi-Fi/LTE, IPv4-only CGNAT (отказ или отдельный explicit proxy), HTTPS/TLS passthrough, QUIC/ECH/SVCB/DNSSEC, idle/expiry/failed DB, нагрузка и откат.
8. **Коммерческий GO:** только после packet capture сверки байтов, учёта после refund и восстановления утраченных HELD с удостоверенной остановкой сетевого потока. Иначе платный DNS с учётом гигабайт = NO-GO.

## Чего делать нельзя

- Не включать IPv6 временной командой до предоставления провайдером маршрута.
- Не менять /etc/network/interfaces, firewall, nginx, DNS, WireGuard, sysctl, cloud-init на работающем сервере в ходе read-only анализа.
- Не считать /64 автоматически полностью используемым, не выводить реальный префикс в публичных логах.
- Не публиковать индивидуальные DNS-only ссылки, обещая работу на IPv4-only клиентах и точный подсчёт HTTPS гигабайтов.

**Итог:** у RU есть реалистичная публичная опция /64, но выделение адресов и reboot являются отдельным одобренным действием в биллинге провайдера. Пока они не совершены, можно лишь сохранять проверки и запланированный план подключения.
